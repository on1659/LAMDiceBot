# 홈 리뉴얼 독립 검토와 11번 목업

작성·수정: Codex · 2026-10-04. 서버 선택을 먼저 해야 한다는 사용자 피드백을 반영해 11번을 수정했다. 대상: 실서버 첫 진입 화면, 기존 목업 1~10, 새 목업 11. 사용자 조사 결과가 아니라 실제 브라우저 관찰과 구현 검토에 근거한 전문가 평가다.

## ① 한 줄 결론

**11번은 내 서버나 자유 방을 먼저 고르고, 선택한 곳에서 방을 만들거나 합류하는 흐름으로 수정했다.** 첫 화면은 장소 선택에 집중하고, ‘경마 방 만들기’와 열린 방은 선택한 서버의 로비에서 보여준다. 필요한 서버 선택을 생략하지 않으면서 글과 조작을 줄이는 것이 기준이다.

## ③ 10번의 약점

1. **‘경마’가 설명 보기인지, 게임 선택인지, 방 생성인지 불명확하다.** 그림의 크기는 누를 곳을 설명하지만 결과까지 설명하지 않는다. ‘방 만들기’라는 짧은 동사에 글자 예산을 쓰는 편이 낫다. 오조작 후 나가기·빈 방 정리까지 포함해야 실제 비용을 평가할 수 있다.
2. **‘링크 복사됨’은 실제 성공과 다르다.** `openRoom()`은 복사 호출 없이 성공 문구부터 표시한다. 복사 버튼도 고정 경마 URL을 쓰고 실패를 무시한다. 방 생성 1탭을 공유 완료 1탭으로 읽으면 안 된다. 복사 실패·복사 가능한 예시 링크·실제 공유 완료를 분리해야 한다.
3. **서버 선택 시트의 상태가 완성된 흐름은 아니다.** 참여코드 서버를 누르면 입력 없이 가입됨으로 바뀌고, 새 서버는 이름·설명·코드 입력 없이 자동 생성된다. 시트 하나에 담을 수 있다는 구조적 가능성과 업무 흐름을 해결했다는 주장은 다르다. 승인·거절·강퇴 같은 관리는 별도 관리 화면으로 분리할 수 있다.
4. **처음 온 사람이 열린 방을 골라도 목적지가 유지되지 않는다.** 이름 확인 전에 선택한 방의 게임만 저장하고, 확인 후 방 제목·참여 인원은 전달하지 않는다. 초대 참여자에게는 새 방 생성 속도보다 원래 방을 잃지 않는 것이 중요하다.
5. **기본 상태의 통과가 모든 상태의 통과는 아니다.** 로그인하면 서버 선택 버튼이 추가되어 **40자·7개**가 된다. 회원 상태는 6개 기준을 넘는다. 화면의 기록 범위를 사용자가 알아볼 수 있는지도 함께 봐야 한다.
6. **네 게임에 맞춘 2×2 구성은 늘어나는 게임을 위한 답이 아니다.** 다섯 번째를 넣으면 대칭과 엄지 도달 범위가 달라진다. 행 수를 계속 늘리면 열린 방과 시작 동작이 화면 아래로 밀린다.

## ④ 11번: 서버부터 한 판

**‘어디서 놀까요?’에서 내 서버나 자유 방을 먼저 고른다.** 로그인한 사람은 가입된 서버를 누르고, 게스트는 자유 방을 누르거나 로그인해 내 서버를 확인한다. 서버 찾기·만들기는 보조 행동으로 둔다. 지난 서버를 자동 확정하거나 첫 화면에서 곧바로 경마 방을 만들지 않는다.

장소를 고르면 서버명과 기록 여부가 보이는 로비로 이동한다. 로비에는 ‘경마 방 만들기’, ‘다른 게임’, 열린 방 두 개를 표시한다. 열린 방을 한 번 더 펼치는 단계 없이 원하는 방에 바로 합류한다. 서버를 바꿀 때는 첫 선택 화면으로 돌아간다. 방에서 나가면 선택한 서버의 로비로 돌아온다.

목업은 HTML 한 파일이며 서버 API에 연결하지 않는다. 방·서버·로그인·가입은 고정 예시를 이용한 흐름 시연이다. 실제 게임 결과, 인증, 권한 검증, 기록 저장, 멀티플레이 동기화가 구현됐다는 뜻은 아니다. 선택 사항인 12번은 만들지 않았다.

### 상태별 실측과 탭 수

수정 후 375×812와 1200×900에서 각각 처음·단골·로그인 상태를 측정했다. 처음·단골은 **51자·5조작**, 로그인은 **52자·5조작**이며 모두 1화면으로 60자·6개 기준을 통과한다. 서버 선택 버튼이 첫 화면에 보이며 가로 넘침은 없다. `node mockups/measure.js`의 현재 11번 출력은 다음과 같다.

```text
  11 |           51 |         5 |        51 |          1 | 통과 | LAMDice — 서버부터 한 판
```

첫 화면의 서버 선택부터 방 대기 화면까지 센다. 입력 칸 선택·타이핑과 상태 전환용 목업 바 클릭은 제외한다. 기본 게임은 경마다.

| 상태 | 기본 경마 새 방 | 열린 방 합류 | 다른 게임으로 새 방 |
|---|---|---|---|
| 처음 | 자유 방 → 만들기 → 이름 확인, **3탭** | 자유 방 → 방 선택 → 이름 확인, **3탭** | 자유 방 → 다른 게임 → 게임 선택 → 만들기 → 이름 확인, **5탭** |
| 단골 | 자유 방 → 만들기, **2탭** | 자유 방 → 방 선택, **2탭** | 자유 방 → 다른 게임 → 게임 선택 → 만들기, **4탭** |
| 로그인 | 가입된 서버 → 만들기, **2탭** | 가입된 서버 → 방 선택, **2탭** | 가입된 서버 → 다른 게임 → 게임 선택 → 만들기, **4탭** |

이름을 바꾸면 입력 조작이 추가된다. 서버 찾기·가입·참여코드·새 서버 생성·로그인이 필요한 경로에는 해당 절차가 추가된다. 이전 11번의 처음 2탭·단골 1탭은 서버가 미리 선택되어 있다는 가정이었다. 수정 후 생성 경로에는 서버 선택 1탭이 늘어난다. 합류 경로는 로비에 열린 방을 바로 보여주어 기존과 같은 탭 수를 유지한다. 경마 외 게임은 게임 선택에 2탭을 더 사용한다.

### 검증 범위

- 모바일·PC에서 처음/단골/로그인 상태의 서버 선택 → 방 생성 → 방 나가기 → 로비 → 기존 방 합류 → 서버 선택 복귀를 클릭 검증했다. 이름 없는 첫 방문자의 방 생성·합류는 이름 확인을 거친다.
- 처음 온 사람이 기존 방에 합류할 때 원래 방 제목과 참여자를 유지하고, 인원을 2/8에서 3/8로 표시한다.
- ‘내 서버’에서 로그인해도 서버 선택 화면에 머물며, 사용자가 가입된 서버를 눌러야 해당 로비로 이동한다.
- 가입된 서버 선택, 참여 가능 서버 가입, 승인 대기, 잘못된 코드 오류와 올바른 코드 입력, 새 서버 생성 후 로비 이동, 다른 게임 선택 후 방 생성을 확인했다.
- 라이트·다크 및 로비 화면을 캡처했다. 이번 흐름 검증의 JS 예외는 0이며, 모바일·PC에서 가로 넘침이 없었다.

수정 후 검증 자료는 `/tmp/serverfirst-qa.json`, 화면 캡처는 `/tmp/serverfirst-{375,1200}-{new,return,member,dark,lobby}.png`에 있다. 스크린리더 실사용과 모바일 실제 키보드 테스트는 수행하지 않았다.

최초 버전에서는 이름 확인 후 선택한 방·기존 참여자 유지, 가입·코드·승인 대기, 서버 생성, 로그인·회원가입, 게임 선택, 클립보드 성공·실패, Escape·포커스 복귀를 검증했다. 최초 검증 자료는 `/tmp/lam-home-qa-results.json`, `/tmp/lam-home-review-shots/measurements.json`, `actions.json`, `8-actions.json` 및 `/tmp/lam11-{375,1200}-{new,return,member,dark}.png`에 남긴 로컬 임시 산출물이다. 이 자료를 수정 후 화면의 검증 결과로 재사용하지 않는다.

## ⑤ 열린 질문에 대한 입장

### 1. 처음 온 사람의 이름

**이름 한 칸을 방에 들어가기 직전에 확인받는다.** 제안 이름은 입력 비용을 줄이지만 내기 결과에서 누군지 알아보는 비용까지 줄이지는 않는다. ‘결과에 표시될 이름’이라는 목적을 짧게 밝히고 수정할 수 있게 한다. 자동 이름으로 즉시 입장하는 1탭을 기본으로 채택하지 않는다. 첫 화면 이름 칸은 게임을 시작할 생각이 없는 초대 탐색자에게도 입력을 요구하므로 뒤로 미룬다.

수정한 11번의 ‘처음 3탭’은 자유 방 선택부터 시작해 제안 이름을 그대로 수락할 때의 행동 버튼 수다. 이름을 수정하면 입력칸 탭·키보드 조작이 추가된다. 보고할 때 버튼 탭 수와 이름 입력 부담을 따로 표기한다.

### 2. 로그인한 단골의 첫 화면

**가입된 서버를 첫 화면에 보여주고 사용자가 직접 고르게 한다.** 지난 서버는 목록 우선순위에 활용할 수 있지만 자동으로 확정하지 않는다. 서버를 고른 다음 로비에서 서버명과 ‘기록 남음’을 확인하고 방을 만들거나 합류한다. 자유 방도 같은 첫 화면에서 선택할 수 있다. 운영 반영 시에는 탈퇴·강퇴·삭제 여부와 권한을 서버에서 다시 확인해야 한다.

### 3. 로그인과 회원가입 통합

같은 한 장에 넣는 것은 가능하지만 **없는 이름이면 즉시 가입시키는 것은 반대**한다. 오타를 새 계정으로 확정할 수 있기 때문이다. 이름·숫자 암호코드 입력 UI는 공유하고, ‘이 이름으로 가입’ 행동만 명시적으로 분리한다. 기존 이름에 다른 암호코드를 입력한 경우에는 새 계정을 만들지 않는다. 목업의 상태 변경은 실제 인증 성공을 증명하지 않는다.

### 4. 첫 화면의 열린 방

**서버 선택 후 로비에서 열린 방을 바로 보여준다.** 첫 화면은 서버 선택에 집중하고, 로비의 방 목록을 별도 버튼이나 모달 뒤에 숨기지 않는다. 링크를 잃은 사람도 장소를 고른 다음 현재 방에 바로 합류할 수 있다. 초대 URL로 온 경우에는 홈을 거치지 않고 해당 방의 이름·게임·참여자를 보여주고 합류시킨다. 새 방 생성과 열린 방 합류는 별도의 전환 지표로 측정한다.

### 5. 무엇을 걸까

**방 안으로 옮긴다.** 커피·점심은 게임 시작의 선행 조건이 아니다. 필요하면 방 이름이나 선택형 내기 메모에 넣되, 같은 내용을 두 군데 입력시키지 않는다.

### 6. 광고와 60자·6개

제품 UI 60자·6개는 유지하되, 광고가 실제로 노출된 화면도 별도로 검증한다. 광고를 측정에서 빼놓고 사용자가 보는 화면 전체가 간결하다고 주장하지 않는다. CTA와 광고를 가까이 붙이지 않고, 공간이 부족하면 첫 화면을 억지로 광고와 공유하지 않는다. 목업에는 광고 호출을 넣지 않았다.

운영에서는 AdSense 콘솔의 페이지 제외·영역 제외·광고 형식 설정을 확인한다. 공식 문서상 영역 제외는 **인페이지 자동 광고에만** 적용되므로 앵커 등 다른 형식까지 없어지는 것으로 가정하면 안 된다. 페이지 제외는 fragment·query 조건을 지원하지 않으므로 같은 URL의 모달/방 상태만 CSS로 숨기는 방안에 의존하지 않는다. 기존 ‘코드로 못 끈다’는 기록을 모든 광고 방식의 기술적 불가능으로 확대하지 않는다. 근거: [Google 영역 제외 안내](https://support.google.com/adsense/answer/12626543?hl=en), [페이지 제외 안내](https://support.google.com/adsense/answer/9262311?hl=en), [자동 광고 설정](https://support.google.com/adsense/answer/9305577?hl=en) (2026-10-04 확인).

### 7. 게임이 다섯 개 이상이면

서버 선택 후 로비에서 기본 CTA 하나와 ‘다른 게임’ 목록을 유지한다. 목록 안에서 그림·게임명·베타/준비 중 상태를 보여준다. 출시 게임이 늘어도 첫 서버 선택 화면과 로비의 조작 수는 늘지 않는다. 단, 경마 외 게임의 반복 이용자는 10번보다 느려진다. 실제 게임 선택 분포를 확인한 뒤 최근 게임을 기본 CTA로 복원할지 판단한다. ‘경마가 인기’라는 설명만으로 모든 사용자가 경마를 원한다고 단정하지 않는다.

### 8. 다크 스킨과 색 체계

**운영의 의미별 토큰 체계를 유지한다.** 표면·본문·보조 글자·선·버튼 바탕·버튼 위 글자를 분리한다. 픽셀 그림은 그대로 두고 UI의 밝기만 바꾼다. 목업은 허용된 단일 HTML 범위에서 라이트/다크 변수를 함께 제공한다. 운영 반영 시에는 `css/theme.css`의 공통 토큰에 대응시켜야 하며, 목업 팔레트로 기존 스킨 여섯 개를 덮어쓰지 않는다. 이번에는 실제 운영 테마 파일을 수정하지 않았다.

## ⑥ Claude와 의견이 갈리는 지점

- **30자라는 수치 자체가 10번의 승리를 확정하지 않는다.** ‘방 만들기’, ‘기록 없음’처럼 행동 결과를 설명하는 짧은 글은 추가하는 편이 오조작을 줄일 수 있다.
- **게임 선택 1탭과 친구가 있는 올바른 방에 도달하는 것은 다르다.** 자동 복사 문구와 초대 합류 동작을 검증하지 않은 탭 수는 실제 효율을 과장할 수 있다.
- **1~5번이 색·서체만 다른 것은 아니다.** 배치, 첫 행동의 위치, 입력과 CTA의 결합 방식도 비교해야 한다. 다만 첫 화면의 읽기 부담이 크다는 문제는 공통이다.
- **60자·6개는 유용한 설계 제한이고 사용성 점수는 아니다.** 생성/합류 성공률, 첫 행동 오해율, 이름 수정률, 잘못된 서버 생성 후 이탈률, 공유 성공률, 초대받은 사람의 합류 완료 시간을 더한다. 사용자 테스트 전 목표치를 검증된 사실처럼 쓰지 않는다.
- **탭 1회가 언제나 최선은 아니다.** 이름 확인과 권한·참여코드 확인은 필요한 단계다. 기록 위치와 행동 결과를 알 수 있을 만큼은 읽을 수 있어야 한다.

### 측정 방법에서 주의할 점

`measure.js`는 목업 바를 제외하려고 가시 범위를 `bar.bottom + innerHeight`까지 잡는다. 따라서 실제 화면 하단보다 목업 바 높이만큼 아래도 포함한다. 값·placeholder·이미지 속 글·CSS 생성 문구는 텍스트 노드와 다르므로 숫자가 사용자의 읽기 부담 전체를 나타내지는 않는다. 이번에는 기존 측정기를 수정하지 않고 동일 조건의 수치를 제시하며, 별도로 실제 첫 화면의 CTA 가시성과 가로 넘침을 확인한다.

9번은 전용 바 탐지가 되지 않아 측정 결과에 테스트용 문구와 링크까지 포함된다. 7번의 고정 내비 뒤 콘텐츠와 내부 스크롤, 실서버 오버레이 뒤 DOM도 단순 문서 길이로 평가할 수 없다. 기존 파일을 고치지 않는 범위이므로 원래 출력은 보존하고 한계를 명시했다. 2·3번의 바 제거 후 CTA 좌표는 산술 비교이며, 바를 실제로 제거한 화면을 다시 렌더한 결과는 아니다.

💡 lesson 후보: 첫 화면 지표는 오버레이 뒤 DOM과 목업 조작 바를 정확히 분리하고, ‘방 생성 완료’와 ‘로비 도착’의 완료점을 통일해야 한다. 이번 수정 허용 범위에 따라 lessons 파일에는 추가하지 않았다.
