# 데구리 랜덤 트랙 — 구현 전 타당성 검토

작성일: 2026-09-21. 요청한 인계 §3의 11개 질문에 대한 코드 감사 및 현재 트랙 기준선 측정.
대상: `feature/marble-run`의 **현재 미커밋 작업 포함**. HEAD만으로 실험 소스를 식별할 수 없으므로 [baseline.json](baseline.json)에 실제 시뮬레이터 SHA-256과 Node 버전을 기록한다.

## 실제 서비스 한도 정정 — 사용자 확인 후 추가

**현재 정상 게임 경로의 최대는100마리다.** 방 입장은 최대50명(`socket/rooms.js:696`), many 프리셋은 `perMax:8,total:100`(`socket/marble-sim.js:24`)이며 실제 시작은 `crowdBallsPerPlayer`를 사용한다(`socket/marble.js:99`). 참가자2..50명과 네 프리셋을 전수 계산했으며 최대100마리였다(25명×4 또는50명×2).130마리 한도는 현재 설정에 없다.

`MAX_BALLS=200`은 시뮬레이터 내부 상한이며 아래200마리 실험은 정상 설정으로 도달하지 않는 범위 밖 스트레스 테스트다. **200마리 캡 문제를 랜덤 트랙 출시 전 필수 해결 조건으로 제시한 이전 결론은 철회한다.** 우선 실제 설정의100마리·many(독수리3마리)에서 기준선을 측정해야 한다. 이번에 실행한120판에는 해당 조건이 없으므로 실제 최대 조건의 안전 여부는 아직 판단할 수 없다. 아래200마리 측정값 자체는 유효한 스트레스 참고 자료로 보존한다.

## 판단

**고정 머리 + 중간 7종 각 1개 + 고정 꼬리 구조는 가능하다. 다만 현재 인계안 그대로 구현·출시하기에는 검증되지 않은 전제가 있다.**

1. 실제 최대100마리 조건의 추가 검증이 필요하다. 범위 밖200마리 스트레스에서는 캡이 발생했고 기존 테스트의 `ALL PASS`가 캡 미도달 보증이 아니라는 점도 확인했다.
2. 셔플은 대부분 데이터 재배치로 가능하지만, 반전에는 렌더 수정과 풍차 회전 계약 수정이 필요하다.
3. 구덩이 분출·스프링·워프는 앞 모듈까지 영향을 준다. 동일 모듈 목록이라는 이유만으로 길이·처리량이 유지되지는 않는다.
4. `trackSeed` 공유는 필요하지만 전체 프리뷰 일치·진행 중 재입장 복원까지 자동 해결하지 않는다.

권장 진행 순서: **실제 최대100마리·many 기준선 확인 → 원본과 동일한 모듈 추출 → 셔플 검증 → 반전 검증**. 실제 범위에서 병목이 재현될 때 그 문제를 먼저 해결한다. v2 부분 선택과 세분화는 이후다. 이번 작업은 분석이며 게임 코드는 변경하지 않았다.

## 증거와 재현 범위

- 기존 `node AutoTest/marble-determinism-test.js`: ALL PASS. 그러나 마지막 200마리·seed=5 케이스는 `simEnd=120000`, `cap hit: true`.
- 추가 실험: seed 1..40, 현재 순서 유지. 18마리 seeded/normal, 200마리 seeded/normal, 200마리 rng=null/normal의 120회.
- seeded는 기존 댐 틈·플립플롭 초기 방향·경사 틈·워프 통나무 난수다. **모듈 순서 셔플 실험이 아니다.**
- 출발 인원은 18마리=6명×3, 200마리=50명×4로 구성. 후자는 시뮬레이터의 부하 조건이며 현재 UI crowd 프리셋을 통한 50명 방의 실제 설정과는 다르다. 모두 독수리 2마리인 normal로 고정했다.
- 계측은 소스를 메모리에 로드하여 STUCK 킥과 캡 직전 상태만 추가 수집한다. 원본 파일은 수정하지 않는다. 소인원 seed1 및 캡 재현 seed5에서 계측값을 제외한 **전체 반환값이 원본과 일치**함을 검증했다.
- 실행: 저장소 루트에서 `node docs/analysis/marble-random-track-2026-09-21/baseline.cjs`. 현재 소스가 바뀌면 출력 파일이 새 기준선으로 덮어써지므로 이전 JSON을 비교용으로 보존할 것.
- 원본 PNG 6종 확인 및 렌더 소스 감사 수행. 실제 반전 트랙의 브라우저 시각 검증, 순서별 시뮬레이션, 운영 컨테이너 성능 검증은 미수행.

틈은 중심 간 거리가 아닌 충돌 표면 간 최단 거리로 정의한다. 현재 말뚝끼리32px, 말뚝-외벽42px, 꼬리 통나무-외벽50px, 봉우리 옆30px, 끊긴 경사 틈40px도 존재한다. 따라서 “전 구간 틈≥44, 통나무-벽≥80”는 현 코드 불변식이 아니다. 신규 이음매의 설계 목표와 기존 장치 내부의 검증된 형상을 구분해야 한다.

컨베이어 끝60px는 과거40px 아치 문제를 피한 국소 튜닝이다(270행). 이를 모든 깔때기 안전폭으로 일반화할 수 없다. 댐의2500ms 제한은 댐 판자를 없앨 뿐, 위 깔때기에서 형성된 공 아치를 제거하지 않는다.

각 유향 이음매에서 다음을 검사한다:

- 이전 마지막 장애물과 다음 첫 장애물의 **충돌 표면** 거리. 움직이는 팔은 전 회전 영역 포함.
- 공 중심이 지날 수 있는 경로: 반경14만큼 장애물을 확장한 뒤 통과 경로 확인. 잠든 공의 반경17은 밀집 실험에 포함.
- 좁은 채널 밖으로 누적 밀림, 벽 외부 체류, 장시간 전진 없는 무리.
- 입구 유량·좌우 쏠림·일괄 방출. “외벽 폭500”과 “공이500폭에 고르게 분포”는 다르다.

특히 구덩이 분출은 실제 **4열**이다(`floor((160−28)/32)=4`, 652행). k마리 동시 분출 시 맨 위 공은 `pit.y − (ceil(k/4)−1)×30`으로 놓인다. k=200이면1470px 상향 재배치가 가능하다. 이는 정적 상한이며 실측 최대 분출 수는 기준선 표를 따른다. 모듈 높이670px만으로 영향 범위를 설명할 수 없다.

## 2. 200마리 처리량과 최악 순서

아래는 정상 최대100마리를 초과한 스트레스 결과다. 실제 게임의 실패로 일반화하거나 출시 차단 근거로 삼지 않는다.100마리·many 검증에서도 **자연 골인과 캡 강제 정산을 분리**해야 한다.

캡에서는 미도착 공도 `finishBall(SIM_CAP_MS, b)`로 전부 finishOrder에 추가된다([sim](../../../socket/marble-sim.js) 983–989행). 따라서 `finishOrder.length===200`은 완주 검증이 아니다. 최소 검사값은 `simEndMs<SIM_CAP_MS`와 `forcedCount===0`이다. 정확히 캡 시각 자연 골인과 강제 정산도 계측에서는 구분한다.

우선 탐색할 순서 조건:

- 말뚝밭 첫 배치: 지금 관측된 출발 직후 정체의 기준선.
- 그릇→댐→장치골짜기: 중앙 집중 출구와 연속 좁은 입구.
- 댐→장치골짜기→갈래골짜기: 일괄 방출 뒤 목·컨베이어·워프.
- 풍차 경사로→댐, 갈래골짜기→장치골짜기: 한쪽 쏠림/역류 뒤 깔때기.
- 댐→햇볕 및 햇볕을 마지막에: 분출/출구 속도와 늦은 낮잠 영향.
- 장치골짜기→댐/햇볕: 마지막 팬 영향띠의 다음 모듈 침범.

위는 **최악 후보**이며 최악이라고 실증한 순서는 아니다. 생성기가 없는 현재 코드에 임의 좌표 이동을 덧대면 외벽 분할·충돌 순서·난수 소비까지 섞여 결론이 오염된다. 이번에는 원본 기준선을 확보했고, 순서별 비교는 아래 sweep 계약을 제시한다.

## 3. 경주 길이: simEnd와 체감 시간을 따로 측정

“7모듈을 모두 포함하면 길이48~62초가 불변”은 근거가 부족하다. 각 장치의 최대 대기시간은 경주 전체의 최대 지연을 더해서 계산할 수 있는 독립 항이 아니다.

- 늦게 도착한 공은 이미 터진 댐을 건너뛴다. 앞 모듈이 군집을 모으거나 분산하면 댐 체류가 달라진다.
- 팬·풍차·두더지·구멍 뚜껑은 경주 시각의 위상을 사용한다. 순서를 바꾸면 진입 시점과 위상이 함께 변한다.
- 벌집 효과는 최초 진입 후 단발 시간창이다. 뒤처진 공은 효과를 놓칠 수 있다.
- 구덩이는 주기 분출 및 상향 재배치, 스프링은 반복 역류를 만든다.
- 햇볕의 낮잠은 꼴찌와 끝에서 두 번째 공의 간격을 바꿔 cut/fast/slow 전환에 영향을 준다.

기록값: `simEndMs`, `durationMs`, `cutMs`, fast/slow 구간, 첫/중간/마지막 꼬리 진입, 두 번째 마지막 골인, 자연 미완주 수. 사용자 목표50±8초는 **재생 시간 durationMs 기준인지** 명세에서 먼저 고정한다. 권장은 durationMs를 사용자 경험 지표로, simEndMs를 처리량 지표로 쓰는 것이다. 룰렛·카운트다운·결과 대기를 포함하는 방 전체 시간은 별도다.

캡 도달 값120초는 자연 완주시간의 측정값이 아니라 검열된 값이다. 이를 포함한 p95=120초를 “대부분120초에 완주”라고 해석해서는 안 된다.

## 4. 반전: 데이터와 렌더 계약

인계의 변환표를 다음처럼 보완한다.

| 필드 | 변환 |
|---|---|
| 점 x, beaverX, spots[].x, decor.x | W−x |
| zone | x′=W−x−w; 크기 유지 |
| wall 선분 | 두 끝점을 각각 반사. 끝점 순서 보존 가능 |
| belt/dam/gap/bounds 구간 | x1′=W−x2, x2′=W−x1 |
| 벡터 각도 | π−angle |
| belt.speed; fan/mole/flipflop.dir | 부호 반전 |
| 풍차 | 회전 방향 반전; 일반 각도 위상은 π−phase |
| warp.idx/pair/color, hidden, 크기 | 유지. 연결된 숨은 벽도 함께 반사 |
| 시간 phase/period/cooldown | 유지. 각도 phase와 구분 |

**wall은 x1<x2를 가정하지 않는다.** 벽 정규화가 필요하면 `(x1,y1)`과 `(x2,y2)` 전체를 교환한다. x만 교환하면 경사 자체가 바뀐다. 시뮬레이터의 `closestOnSegment`/`collideSegment`가 근거다(417, 551행).

## 5. bounds 계약

`track.bounds` 수신은 이미 구현되어 있다(sim514, 943–950행). 권장 계약은 **생성기의500폭 전역 bounds 1개 + 각 모듈의 좁은 직선 채널 bounds**다. 모듈은 로컬 y로 반환하고 합성 시 이동한다.

- bounds는 충돌 뒤 x를 강제 보정한다. 같은 y에서 겹치는 구간은 교집합 의미여야 한다.
- 현재 루프는 순차 clamp이며 양끝 y를 포함한다. 전역과 내부처럼 포함 관계일 때 안정적이다. 서로 불일치하는 구간 중첩은 생성 시 거부한다.
- 활성 구간 교집합 폭≥2r, 이음매 y 누락 없음, 인접 끝점 일치 검증.
- 실제 반경은 roll 공의14를 기준으로 하되 잠든 공 등의 위치 제약은 별도 정책이다. 현 clamp는 roll 상태만 적용한다.

현재 bounds는 댐 깔때기 경사, 장치골짜기120폭 목, 구멍밭420폭 외벽을 모두 감싸는 정밀 형상이 아니다. 공-공 충돌은 y도 밀어내므로 내부벽을 통과한 공이 넓은 전역 bounds 안에 있으면 복구되지 않는다. **외곽 seam의 누출 방지와 내벽 관통 방지는 다른 문제**다. 경사별 xMin(y)/xMax(y)나 다각형 bounds 도입은 물리 변경으로 분리 검증한다.

긴 외벽을 여러 선분으로 자르면 접점에서 충돌 처리 횟수가 바뀔 수 있다. 형상 보존만으로 프레임 동일성을 선언하지 않는다.

## 6. trackSeed 수명·프리뷰·복원

권장: `trackSeed`와 `raceSeed`를 독립적으로 생성한다. 지도 RNG를 공개하더라도 raceSeed와 단순 XOR 관계를 만들지 않는다. 순서/반전/모듈 내부 RNG도 안정적인 모듈 ID별로 분리하면 순서만 바꾸는 비교가 가능하다.

| 전환 | trackSeed 처리 |
|---|---|
| 새 방 첫 idle 프리뷰 / 첫 시작 | null이면 한 번 생성. 0은 유효 시드 |
| 상태 요청·준비·선택·crowd·방장·재연결 | 유지 |
| idle→playing | 프리뷰 seed 사용 |
| playing→finished | seed와 완성 timeline 유지 |
| finished→idle 다음 판 준비 | 새 seed 한 번 |
| finished→playing 직접 시작 | 새 seed 한 번. reset을 거치지 않는 경로도 처리 |
| 시뮬 실패→idle 재시도 | 동일 seed 유지 |
| 방 삭제·프로세스 재시작 | 폐기, 새 방에서 새 seed |

수동·강제·예약 시작이 모이는 `startMarble`에서 수명 계약을 보장한다. finished에서 직접 시작을 허용하므로 reset에서만 갱신하면 맵 반복이 생긴다. 재시도와 성공적인 다음 판을 구분한다.

현재 프리뷰는 준비자 또는 동물 선택자를 **1마리씩**, 실제 경주는 준비자만 crowd별 복수 마리로 만든다(marble.js265–271, 92–99, 124–125행). 같은 seed라도 출발대 높이, 구멍 open 시간, 통로 rows가 ballCount에 따라 달라진다. crowd는 독수리 수도 바꾼다. v1의 간단한 약속은 **“중간 모듈 구성·방향·장치 배치는 같고 마릿수 의존 값은 현재 참가 조건에 맞춘다”**다. 전체 track 일치가 필요하면 preview 생성에 예상 경기 마릿수를 전달하고 dim 동물의 배치는 별도로 설계한다.

캐시가 필요하면 키는 `(trackVersion, trackSeed, ballCount, crowd)`. seed만으로 완성 track을 캐시하면 값이 낡는다. 완성 geometry를 전달하는 기존 프로토콜을 유지하고 과거 timeline은 새 seed로 재생성하지 않는다.

**재입장 복원 정정:** 최초 reveal에는 track이 포함되나(marble.js143), reveal 재전송은 없다(emit162 한 곳). `requestState`도 timeline을 제외한다(344–349). 클라도 진행 중 재입장 재생 불가를 명시한다(js/marble.js943–948, 1148–1151). 현재 탭의 다시보기는 메모리의 이전 reveal이다. 복원 기능을 추가한다면 `roundId`, `revealedAt`, 경과시간 동기화, reveal 이전 비공개 상태를 설계해야 한다. playing은 룰렛 단계부터 켜지므로 phase만 보고 timeline을 보내면 조기 공개된다.

**grace 정정:**300초는 Socket.IO transport recovery 설정(server.js28–29)이다. 빈 방 grace 기본값은120초이며 환경변수로 바뀐다(config/index.js12). 운영값은 확인하지 않았다. `rooms={}`는 메모리이므로 컨테이너 재시작을 견디지 않는다(server.js52). seed만 저장해도 참가자/상태/타임라인/시각까지 복원되는 것은 아니다.

## 8. v2 부분 선택 예산 모델

높이를 시간으로 바로 환산하지 않는다. 목표50±8초는 우선 **durationMs 42..58초**로 정의하는 것을 제안한다. 이는 합의·검증 전 설계 목표다. 현재 전체 트랙 기준선도 별도로 비교해야 한다.

측정 방법:

1. 5ms 내부 단계에 모듈 진입/퇴출 계측을 추가한다. 첫 진입, 첫 하단 통과, 마지막 하단 통과, 재진입 횟수, 상태별 체류, 이전 모듈로의 재배치 이벤트를 분리한다. 200마리의100ms 샘플 프레임은 순간속도·짧은 체류를 정확히 복원하지 못한다.
2. 모듈별 평균/중앙 통과시간은 공 단위로, 꼴찌 지연은 **판 단위의 최종 완료 경로**로 측정한다. 모듈별 p95를 단순 합산하지 않는다.
3. 같은 layout/physics seed와 모듈 내부 seed를 쓰는 paired 실험으로 모듈 포함/제외 차이를 측정한다. 이음매·crowd·위치에 따른 차이를 함께 기록한다. 실행 경로가 바뀌면 같은 RNG seed라도 이후 난수 소비는 달라질 수 있으므로 완전한 개체별 대응이라고 해석하지 않는다.
4. 초기 모델: `duration ≈ 고정 꼬리 비용 + 선택 모듈 비용 + 주요 인접쌍 보정 + 마릿수 보정`. 물리적 높이 예산은 화면 길이 제약으로 별도 관리한다.
5. 고르지 않은 seed/순서로 검증하고 오차 범위와42..58초 내 비율을 보고한다. 모델로 걸러낸 후보도 실제 시뮬 sweep을 통과해야 한다.

7종이면 부분집합127개라 v2 초기에는 통계 모델을 복잡하게 만들기보다 검증된 소수 조합의 카탈로그가 낫다. 부분집합 수에는 순서·반전 경우가 포함되지 않는다.

독수리는 중간 전체 길이보다 꼬리 진입 분산·후보 체류시간·낙하 후 재통과 시간에 영향을 받는다. 예산은 early=`max(2,floor(N×0.06))`, final=`min(2,eagleCount)`이고 두 단계 카운터가 분리된다(sim691–704).200마리 normal이면 이론 상한14회다. “4회±”를 모든 인원의 합격 기준으로 쓰거나 길이 비율대로 예산을 줄이지 않는다.

## 9. sweep 지표·규모·기준선 해시

### 단계별 규모 제안

실서비스 검증은 인원과crowd에서 파생되는 정상 마릿수로 수행한다.100마리 조건은many(독수리3마리)를 사용한다.200마리는 선택적 초과 부하 실험으로 분리한다. 아래768/1920은 순서·seed·반전 조합 수이며 실행시간은100마리 조건을 실측한 후 산정한다.

1. **원본 회귀:** rng=null 경로의 track/frames/events/finishOrder/시간 정보 해시 비교. 작은 인원과 실제 최대100마리·many, 경계60/61마리, crowd별 대표값 포함. 현재 캡 재현도 우선 보존해 변경의 귀속을 분명히 한다.
2. **정적 전수 검사:** 서로 다른7종의 유향 이음매42×좌우 반전4=168개, 머리→중간14개와 중간→꼬리14개로 최소196개 경계 검사. 포트·bounds·충돌표면·센서 영향띠를 검사한다. 성공이 동적 안전을 증명하지는 않는다.
3. **탐색 sweep:** 기준선·역순·병목 연속·햇볕 처음/끝·임의 순서를 포함한 약24개 순서.42개 유향 인접쌍이 실제로 전부 들어갔는지 coverage를 계산하고 누락 시 순서를 추가한다.24×8seed×{18,100}×{무반전,전체반전}=768판을 초기 상한으로 잡는다. 혼합 반전은 다음 단계에서 추가한다.
4. **확인 sweep:** 최악 후보8순서×40seed×{18,100}×{무반전,전체반전,seed별혼합반전}=1920판. 탐색에 쓰지 않은 새 시드를 포함한다. crowd1/3독수리와60/61 경계는 별도 대표 케이스를 추가한다.
5. **시각 QA:** 최악 사례 및 각 반전 장치를 PC/모바일에서 재생. 음수시간·역방향 시크·피날레·미니맵·재생 속도 확인.

7!×2⁷=645,120개 조합 전체를40시드씩 돌리는 것은 초기 QA로 부적절하다. 위1920판 또한 통계적·경험적 확인이지 모든 조합 무고장 보증은 아니다. 실행시간은 기준선 실행 경과시간으로 예상하고 운영 요청 처리와 격리된 오프라인 작업으로 수행한다.

| clamp 횟수·변위, 내벽/외벽 이탈 | bounds 안전성 |
| 진입 vx/vy·유량, 재진입 | seam·부분 선택 예산 |
| nap 수/해당 구역 진입 공 수 |28% 고정 기준 대신 matched baseline 비교 |
| damHit/Burst와 차이, 분출 count·최상단 y | 절대 도착시간과 장치 대기시간 구분 |
| eagleGrab·후보 체류·final 단계 | 인원/crowd별 비교 |
| simEnd/duration/cut/fast/slow 분포 | 물리 종료와 사용자 재생 시간 분리 |
| 실행시간·프레임 수·payload bytes | 서버 계산·전송 비용 |

현재 STUCK 조건은 속도<5가2초 연속이어야 하고 댐·뚜껑 대기는 제외된다(sim883–889). 미세 진동/공끼리 밀기가 계속되면 진전이 없어도 킥이 발생하지 않을 수 있다. 킥을 늘리면 해결된다고 단정하지 말고 진행도 지표와 함께 진단한다.

### 해시 기준선

[baseline.cjs](baseline.cjs)는 실행 환경·실제 소스 해시, 입력 `{balls,seed,track}`, track, frames, events, finishOrder, 전체 timeline의 SHA-256을 기록한다. 계측 데이터·벽시계 실행시간은 timeline 해시에서 제외한다. 소스가 실행 도중 바뀌지 않았는지도 확인한다.

회귀의 핵심은 **리팩터 전 fixture와 리팩터 후 결과 비교**다. 기존 테스트의 “새 코드 두 번 돌려 같음”은 결정론만 확인하며 과거 동작 보존을 확인하지 않는다. rng=null은 순서·무반전 외에 현재 fallback `()=>0.75`가 만든 장치 값, pieces 순서, 선분 분할까지 보존해야 한다. 추출 후 차이가 나면 동작 변경과 단순 추출을 분리하고, 차이를 검토하기 전 fixture를 새 값으로 교체하지 않는다.

## 10. 신규 장치: 회전원판·낙하구멍

- **풍차와 동일한 방사형 팔**이면 기존 windmill 기하를 재사용할 수 있다. 원형 원판의 표면이 공을 회전 방향으로 실어 나르는 동작이면 새 `rotatingDisc`가 적절하다. 현 정지 원 충돌은 접선 운반을 구현하지 않는다. 움직이는 선분의 접점 속도 계산은 재사용 가능하나 원 접촉·마찰 모델은 새로 필요하다.
- **빈 틈으로 떨어짐**이면 wall 조합으로 가능하다. 주기 뚜껑이면 `lidCover`를 공유하는 일반 `trapdoor`가 적절하다. 중간에 holefield를 하나 더 넣는 방식은 싱글턴과 독수리·몸싸움·결승 의미를 깨뜨린다.
- 숨었다 다른 위치로 나옴은 warp 유사 상태/이벤트가 필요하다. 실제 탈락이면 전원 골인 순위 규칙부터 바뀌므로 별도 설계다.
- 현재 manifest에서 해당 명칭 에셋을 확인하지 못했다. 보관 에셋의 존재·경로·그림 의미는 추가 확인 대상이며 가정하지 않는다.

## 11. 미확인 가정 정리와 구현 범위 수정

| 인계 가정 | 검토 결과 |
|---|---|
| 재입장 reveal에 track 포함 | 최초 reveal에는 포함. **재입장 재전송은 미구현** |
| STUCK 기준선 없음 | 이번120회 계측 JSON 확보. no-progress 계측은 후속 필요 |
|200마리 sweep 미실행 | 현재 순서120회 중200마리80회 실행. 순서별은 미실행 |
| 길이 바뀌면 독수리 예산 비례 조정 | 근거 부족. 꼬리 고정 후 후보 체류/밀집부터 측정 |
| sim bounds 수신2~3줄 수정 | 이미 track.bounds 사용 |
| buildTrack 한 함수만 리팩터 | 반전·seed lifecycle·렌더·상수 추출·검증까지 필요 |
| 싱글턴 모듈 전역 상태 | simulate 호출별 지역 상태. 방 간 공유는 아니나 같은 kind 중복 불가 |
| 스프링은 완전 독립 | 장치 cooldown은 독립, 공별 springAt/springOnSince는 공유 |
| 워프방 여러 개 재사용 | idx/pair와 warpDone가 전역 ID 공간을 사용하므로 namespace 필요 |

후속 구현 파일 범위는 `socket/marble-track.js` + `socket/marble-sim.js`(상수/풍차 계약) + `socket/marble.js` + `utils/room-helpers.js` + `js/marble-render.js` + 관련 회귀/sweep이다. 공통 방 상태의 공개 화이트리스트 수정 필요성도 프로토콜 결정 후 확인한다. 재입장 복원을 추가하면 `js/marble.js`까지 범위가 늘며 별도 기능으로 명세하는 편이 명확하다.

모듈 계약은 `{pieces,height,bounds}`에 진단용 `id`, 입출구 포트, 센서/역류 영향 범위를 보태는 방향이 적절하다. 이는 서버 측 검증 메타데이터로 두고 사용자 UI에 구현 정보를 노출할 필요는 없다. 고정 꼬리는 독수리 낙하 위치(`seesaw.y−70`)와 결승 카메라 계약을 함께 보존한다.
