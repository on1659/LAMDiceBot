03harness.md — ultracode와의 관계를 규칙으로

"하네스 vs ultracode"가 아니라 하네스가 ultracode를 검증 엔진으로 쓴다. 범위와 조건이 문서에 박혔다.

  • 쓰기 경로는 항상 직렬 — 근거 명기: STANDARD급 단일 컨텍스트 실측 ~60k 토큰(최악 경마 풀셋 ~150k), 상시 미커밋 트리에서 병렬 쓰기가 사용자 작업을 삭제한 실사고 1건
  • 검증 팬아웃 규칙 6조 — 호출 전 git status · 지시서를 스코프 펜스로 · 읽기 전용 · approve/request-changes 판정으로 수렴(루프 max 3 유지) · 트리아지/lessons 스테이지 전파 · agents 문서 재활용 전 갱신 확인
  • 검증은 읽기 전용이라 훅 결합 문제가 원천 부재 — 패널 최대 쟁점이었던 "Workflow 워커 훅 미발화" 리스크가 이 범위 한정으로 소멸
패널 판정 요약 — 원안(Hands층 전면 Workflow 교체)은 4/4 기각: 유지론 DISAGREE, 축소론·컨텍스트·실증감사 PARTIAL. 교차 심문이 유지론의 "분리 불가" 논거를 실물 transcript로 반증(현행도 트리아지 마커를 서브에이전트에 전파 중). 최종: 검증 한정 하이브리드 + 훅 하드닝 선행, 확신도 HIGH. 참고 실측 — Workflow 리뷰 1회분: 17건 발견 → verify가 오탐 13건 자체 기각 → 확정 4건.

04autogoal — 규모 라우팅을 내장한 진입문

크고 작음을 사용자가 나누지 않는다. 두 축을 분리한 것이 설계의 핵심.

축판정 주체의미
LIGHT / HEAVYautogoal Phase 0 (정찰 후 상향 가능, 하향 없음)계획의 무게 — HEAVY만 계획 패널(Workflow 다관점, 대체: /meeting-codex)을 거쳐 Design Decisions(재론 금지 + 반려 대안 병기)를 goal 문서에 고정
SIMPLE / STANDARD / COMPLEX하네스 트리아지 (Phase 6)구현의 무게 — 패널 결과가 선점하지 못함. 계획은 가볍고 구현은 COMPLEX인 작업(등록 16곳짜리 신규 게임)이 실제로 흔하기 때문

Design Decisions 고정은 bridge-cross 재설계 표류(구현 중 재론으로 메커니즘이 통째로 갈리던 사고)의 재발 방지 장치다.
